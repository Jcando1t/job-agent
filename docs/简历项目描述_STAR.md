# 求职 Agent 项目 —— 简历项目描述（STAR 版）

> 用法：根据目标岗位和简历篇幅，从下面三档里选一档。所有数字如需调整请按真实情况修改。
> 默认技术栈：Python · FastAPI · SQLite · LangGraph · DeepSeek · TypeScript/React

---

## 档位一：一句话概括（适合放「技能/项目」速览）

基于 LangGraph 编排的个人求职工作台：自动分析岗位 JD、检索个人经历、生成有依据依据的定制简历，并内置事实核对与一页篇幅检查，全程由人工审核确认、数据本地化存储。

---

## 档位二：标准版（3~4 条 bullet，适合大多数场景）

**求职 Agent —— 基于 LLM 的个人求职工作台**（Python · FastAPI · LangGraph · SQLite）

- **背景**：针对求职者改简历时普遍存在的「AI 编造经历」与「内容跑题」两大痛点，独立设计与实现一套以「事实依据 + 人工确认」为核心的简历改进工作流。
- **行动**：用 LangGraph 编排「分析 JD → 检索经历 → 生成草稿 → 质量检查」四节点状态图，并以「是否超一页」做条件路由；JD 分析采用可解释的关键词规则，结构化经历按关键词重叠排序，上传简历先按段落切片再按岗位词检索，命中片段和来源编号进入模型提示并展示给用户；暂不引入向量库，大模型按结构化 JSON 生成草稿。
- **结果**：实现三层防编造机制（提示词约束 + 结构化校验 + 本地事实核对），叠加 A4 一页篇幅硬约束与人工审核，显著降低 AI 生成的虚假内容风险；支持 DOCX/Markdown 导出、BOSS 直聘岗位同步与招呼语预填，数据全本地 SQLite 存储。

## 档位三：详细版（5~6 条 bullet，适合项目经验重点展示）

**求职 Agent —— 基于 LLM + LangGraph 的简历智能改进工作台**

- **S（背景）**：个人求职场景中，通用大模型生成简历常出现「虚构经历/数字」与「脱离目标岗位」问题，且缺乏可追溯的依据。
- **T（任务）**：构建一条「有依据、可解释、需确认」的简历改进垂直工作流，实现 JD 理解、经历检索、草稿生成、质量检查与人工审核的闭环。
- **A（行动）**：
  - 用 LangGraph 编排四节点状态图（分析 JD → 检索经历 → 生成草稿 → 质量检查），以「一页篇幅」做条件路由打回修改；节点均为可替换服务，模型与检查器支持注入假实现便于测试。
  - JD 分析用关键词规则拆解「职责/硬性要求/优先条件」，结构化经历按关键词重叠打分（标题权重 ×3）；原始简历本地切片后检索相关片段，模型引用只能指向本次提供的资料编号，检索结果与片段编号会保存在任务快照中。当前是关键词式 RAG，不是向量语义检索。
  - 大模型（DeepSeek）仅负责按结构化 JSON 生成草稿与招呼语，System Prompt 强制「无证据进 missing_information、禁止补造数字」。
  - 质量检查纯本地实现：STAR 检查（行动词+结果词）、事实核对、按字符宽度估算 A4 一页（约 56 行）。
- **R（结果）**：形成「AI 提速、人工拍板」的人机边界，全程数据本地 SQLite 存储、调模型前明确告知数据范围；支持多渠道简历导入（文本/文件/图片 OCR）、DOCX/Markdown 导出、BOSS 岗位同步与招呼语预填（投递仍需人工确认）。

## 面试话术速记（30 秒开场）

> 我做的是一个本地求职工作台，核心是用 LangGraph 把「简历改进」编成一张四节点的状态图：分析 JD、检索经历、生成草稿、质量检查。原始简历会在本地切片并按岗位相关词检索，结构化经历也会按关键词排序；命中的片段和来源编号会进入模型提示并展示给用户。这是可解释的关键词式 RAG，目前没有向量语义检索。再加一页篇幅检查和全程人工确认，减少无依据内容。
